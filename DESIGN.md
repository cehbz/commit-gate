# commit-gate: design

## Model
- **Gate:** the hook directory that each host's global `core.hooksPath` names, so every repo on the host commits and pushes through it from `git init` or clone on. One binary stands behind every hook and command in it. It holds the commit check, the push check and a pass-through hook for every other hook git runs. The agent may change neither the installed gate nor the global setting that names it: a build goes live through a deploy, which only the user's deploy authorization admits. Only the user loosens the gate.
- **Command:** what the user (or the agent, where allowed) runs: a word after the one command `commit-gate`, the only name the gate puts on PATH. The commands are `approve`, `approve-push`, `approve-deploy`, `clear-approvals`, `status`, `enable`, `disable`, `hook-names`, `canonical`, `version` and `install`. The binary's other names are the hooks git and Claude Code run by name (the hook directory's links, `precheck`, `sessioncheck`). Any other word after `commit-gate`, a hook's name included, is an unknown command, and under a name that is neither `commit-gate` nor a hook's (a renamed copy, `go run`'s `cg`) the binary runs no command.
- **Repo state:** how the gate stands in one repo: opted out, enabled, overridden or ungated. Opted out wins. Otherwise the repo is enabled when the `core.hooksPath` git reads there names the gate, from whatever scope; overridden when a repo-local, worktree or command-line value names anything else, an empty value included; and ungated otherwise, which counts as a missing gate. A value set through an include or a matching `includeIf "gitdir:"` reads as git reads it. `commit-gate status` names the state, and for an enabled repo lists its outstanding approvals and whether a push or deploy authorization is live.
- **Enable and opt-out:** `commit-gate enable` clears a repo's own opt-out and repo-local `core.hooksPath` so the global gate applies. While the global `core.hooksPath` is not the gate it refuses and changes nothing, since clearing would leave the repo less gated; an opt-out or override left in another scope is reported with the command that clears it. `commit-gate disable` opts a repo out and is the user's alone, behind confirmation and the launch guard. The agent may enable a repo and may not opt one out.
- **Commit message:** the exact text of a commit, compared in canonical form: carriage returns dropped, trailing whitespace stripped from each line, trailing blank lines dropped. Its identity is the SHA-256 of that form; its subject is its first line.
- **Approval:** the user's assent to one exact commit message in one repo, recorded as the message's identity and subject in the repo's approval list, which the repo's worktrees share. It is single use: the commit it admits consumes it, with any duplicate. Only `commit-gate approve`, run in an enabled repo after confirmation, records one, so the agent's belief that a message was approved admits nothing. `commit-gate clear-approvals` drops every outstanding approval and the push and deploy authorizations.
- **Approval batch:** the messages one `commit-gate approve` records together. `commit-gate approve -F` reads a file whose messages are separated by lines reading `@@COMMIT-GATE-SEP@@`; `--plan` takes every single-line `git commit -m` message quoted in a plan; bare, it takes the pending message, else standard input. Every message is printed in full before confirmation, and recording any approval voids a live push authorization.
- **Pending message:** the last message the commit check rejected in a repo, kept so a bare `commit-gate approve` can approve it. There is one per repo, shared by every session working in it, so a later rejection replaces it. An admitted commit clears it, and so does the bare `commit-gate approve` that records it.
- **Commit check:** the `commit-msg` hook. It runs the repo's own `commit-msg` hook first and fails when that fails. It then admits the commit when the repo is opted out, when an approval for the message exists (consuming it), or when the message equals HEAD's, as an amend's does; otherwise it records the message as pending and rejects the commit, naming its subject and identity. A merge commit is checked like any other, and admitting a commit clears the pending message.
- **Push authorization:** leave for one push from one repo, granted by the user's `commit-gate approve-push` in an enabled repo after confirmation. The push check (`pre-push`) runs the repo's own `pre-push` hook first, then admits a push when the repo is opted out or an authorization exists, consuming it whether or not the remote then accepts the push. A new approval voids it, since a push authorization can't predate the content it pushes.
- **Pass-through hook:** every hook git runs other than `commit-msg` and `pre-push`. It runs the repo's own hook of that name from the repo's native hooks directory, passing its arguments, input and exit status through, so the gate silences no repo hook; the commit and push checks chain to the repo's own hook the same way. A repo hook with no `#!` line runs under `/bin/sh`, as git runs it, and one killed by a signal fails with 128 plus the signal.
- **Confirmation:** the human step behind `commit-gate approve`, `approve-push`, `approve-deploy` and `disable`: a macOS dialog, which works where no terminal is attached, else a prompt on `/dev/tty`, else the command aborts. `--yes` skips it.
- **Launch guard:** the check `commit-gate approve`, `approve-push`, `approve-deploy` and `disable` make of the shell command that launched them, read from the parent process's arguments and from inside Claude Code's `eval '…'` wrapper. It refuses, naming the offender, when that command runs anything besides `cd` and `commit-gate` or computes a command name or argument. An interactive shell passes, an unreadable parent passes with a note, and an unparseable command is refused. It guards against a blind paste of an agent-composed chain, not against an adversary.
- **Precheck:** Claude Code's PreToolUse hook for Bash and the file-editing tools. It decides each call as deny, allow with a reminder, or silent, judging each invocation in a shell command rather than its text. It denies `--no-verify` on a commit or push; a write of the opt-out key; a write of `core.hooksPath` other than one naming the gate, through `git -c`, `GIT_CONFIG_*` or removing or renaming the `core` section included; running `commit-gate approve`, `approve-push`, `approve-deploy`, `disable` or `install`, with `commit-gate` named on PATH or by its path, so the agent installs only through a deploy; a command name or `commit-gate` command word it can't resolve (`commit-gate "$c"`); a write into the protected set; and a command it can't parse. An internal failure denies. A commit or push in an enabled repo that nothing denies is allowed with a reminder of the approval workflow. Its threat model is rationalization, not sabotage: the evasions it leaves open, among them a wrapper in front of `commit-gate` such as `timeout`, `nohup` or `nice`, are listed in `TODO.md`.
- **Protected set:** what the agent may not write: the gate's install directory, a repo's `.git/config`, native hooks and gate state, the user's global git config files (`~/.gitconfig`, `$XDG_CONFIG_HOME/git/config`), and, for the file tools, Claude Code's `settings.json`. The install directory, the global git config and `settings.json` are written by deploy and install, under the user's deploy authorization; the agent may run a deploy, which refuses without one. In a shell command a write is a redirect or a write verb (`rm`, `mv`, `cp`, `tee`, `truncate`, `sed -i`): `cp` is checked at its destination only, so copying out of a protected file is allowed, and `mv` at every operand. The gate's source repo is not protected.
- **Shell command:** a Bash command as the precheck and the launch guard read it: parsed as bash into invocations across every statement, pipeline, subshell and block, recursing into the literal payload of `bash`, `sh` or `zsh -c` up to four levels deep. Each word is literal, literal under `$HOME`, or unresolvable; string and heredoc contents are data and are never matched.
- **Session check:** Claude Code's SessionStart hook. It changes nothing. It tells the user and the model when the host's global `core.hooksPath` is missing or names something other than the gate, with the command that fixes it (naming the included file when an include sets the value), and when the session's repo is overridden, with the step that gates it. Otherwise it is silent.
- **Build:** the gate's binary as built from its source. It records the commit it was built from and whether the source had uncommitted changes, readable from the file without running it, and `commit-gate version` reports both. A build from changed source, or one that records no commit, is from no commit.
- **Release:** a version tag (`vMAJOR.MINOR.PATCH`) on a commit of the gate's public repository. When the user says to install or deploy and the Mac's clone has commits since the target, the agent proposes the version from those changes, by semver (a breaking change to a command or the install raises MAJOR, a new behavior MINOR, a fix PATCH), and `make release VERSION=<tag>` in the clone makes it; with no new commits the deploy uses the target as it is. Release refuses, changing nothing, when the clone has uncommitted changes, when the clone's current branch is not `main`, when the remote has commits the head lacks, when the head is the target's commit, when the tree still holds pending model-level tests, or when `<tag>` is not above every release tag; otherwise it pushes the head and a tag on it in one atomic push, under one push authorization, which is the user's approval of the proposed version, and makes no tag in the clone until that push lands. The agent runs it before the user authorizes the push, as it commits before the user approves: its refusals come first, and the gate's rejection of its push is the ask.
- **Target:** the commit the highest release tag names, read with git (`git ls-remote`) over the repository's public address, which every host can read without credentials. Every host's build is measured against it. Only the target goes live, and only under the user's deploy authorization.
- **Deploy authorization:** leave for one deploy run, granted by the user's `commit-gate approve-deploy` in the Mac's clone after confirmation, behind the launch guard. A deploy consumes it whether or not every host then succeeds. A new approval leaves it, since a deploy puts only the released target live. The agent runs a deploy before the user authorizes it, as it pushes before the user authorizes the push: the refusal is the ask.
- **Deploy:** how a build reaches a host: `make deploy HOST=<host>` in the Mac's clone of the repository, or `make deploy` for every host on its host list, a config file in the clone that git ignores, since the repository is public and names no host: one host per line, a line starting with `#` a comment and a blank line skipped. A host's name is its short host name, except the Mac's, which is `mac`. For each host it builds the target from a fresh copy of the public repository, writing the build outside that copy, for the host's operating system and architecture; it delivers the build to `staging/` in the host's install directory and runs the delivered build's `install`. Only the Mac builds the gate; no host other than the Mac keeps a clone of its repository. Deploy refuses, changing nothing, unless a deploy authorization is live in the clone, and its refusal names `commit-gate approve-deploy`. With no host named and no host on the host list it refuses, and the deploy authorization stays live. It needs nothing from the installed build, so it works on a host with no build or an old one.
- **Install:** `commit-gate install`, a command of the build that puts it live and wires the host to it: the install directory (`~/.local/libexec/commit-gate`), the `commit-gate` link on PATH (`~/.local/bin`), the global `core.hooksPath` (left as it is when it names another directory, and reported) and Claude Code's hooks (`~/.claude/settings.json`). The locations are fixed under the home directory, never taken from where the running build sits. It refuses, changing nothing, unless the build is up to date. The build goes live whole, by replacing the live binary in one step, so the host runs the old build or the new one and never part of one.
- **Version check:** a build is up to date when it is from the target, and out of date otherwise; the host's state is its installed build's, out of date when there is no installed build or it can't report its version. When the target can't be read, or no release exists, the state is unknown. `commit-gate version` prints the build, the target's tag and commit, the state and, when the build is out of date, the fix: `commit-gate approve-deploy`, then `make deploy HOST=<host>`, both in the Mac's clone. It exits non-zero unless the build is up to date. The KB's install script runs it and fails with it, and when there is no installed build, or the build doesn't know `version`, prints the same fix itself; the monitor's out-of-date mail carries it too. The monitor reads the version from the installed file.
- **Machine committer:** a program that commits on its own. It passes `-c core.hooksPath=/dev/null` on each git command, a form the precheck denies to the agent.

## Tests
- Pending mark: `pending(t)`, defined in `pending_test.go` in each package with model-level tests (`cmd/cg`, `confirm`, `gatestate`, `harness`, `launchguard`, `policy`, `shellscan`), called first in a model-level test, skips it until its task removes the call; in the acceptance scripts, `pending` from `tests/pending.sh`, sourced by the script and put before the function that holds a case, does the same. `RUN_PENDING=1` in the environment runs pending tests.
- Model-level tests are every Go test in `*_test.go` except `*_unit_test.go`, run with `go test ./...` (`make test`), and the acceptance scripts `tests/test_*.sh`, run against a build tree with `make accept`. Every git they run reads a temporary global config naming the gate under test, never the user's. A unit test below a domain object's interface goes beside the code in `*_unit_test.go`.
- The acceptance test of install commits a copy of the working tree into a scratch repository and tags it, which serves as both the stand-in target and the source of the build under test, so it passes on a dirty tree and mid-plan. It runs with a temporary home directory, and its private global git config points the public address at the scratch repository (`url.<scratch>.insteadOf`), so the build under test is an ordinary build. The release test runs `make release` against a scratch repository and its scratch remote. The deploy test delivers to a host other than `mac` through stub `ssh` and `scp` on PATH that act on a second temporary home directory; one failing host of two leaves the other live and the deploy exits non-zero.
